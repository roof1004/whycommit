# whycommit 구현 요청

이 문서는 whycommit이라는 오픈소스 도구의 기획 전체야. 끝까지 읽고 아래 "진행 방식"대로 진행해 줘.

## 1. 진행 방식

1. 구현 전에 공식 문서로 현재 스킬·플러그인 형식을 확인해 줘. 기억에 의존하지 말고 직접 읽어 줘.
   - Claude Code 플러그인: https://code.claude.com/docs/en/plugins
   - Claude Code 스킬: https://code.claude.com/docs/en/skills
   - 플러그인 마켓플레이스: https://code.claude.com/docs/en/plugin-marketplaces
   - Agent Skills 표준: https://agentskills.io
2. 그다음 구현 계획, 폴더 구조, 그리고 이 문서에서 모호하거나 빠진 부분에 대한 질문을 먼저 보여 줘. 내가 승인하기 전에는 파일을 만들지 마.
3. 승인 후에는 아래 순서로 한 단계씩 진행하고, 단계가 끝날 때마다 멈춰서 내 확인을 받아 줘.
   1. 레포 뼈대와 README 초안
   2. 학습 노트·상태·설정을 다루는 스크립트와 그 테스트
   3. commit 스킬
   4. quiz 스킬
   5. review 스킬
   6. Claude Code 플러그인 포장과 설치 방법
   7. 11장의 시나리오 전체 검증
4. 단계가 끝날 때마다 무엇을 만들었는지, 왜 그렇게 했는지, 다른 방법은 무엇이 있었는지를 짧게 설명해 줘. 나는 이 코드를 이해하고 넘어가고 싶어.
5. 이 문서와 충돌하거나 더 나은 방법이 보이면 임의로 바꾸지 말고 먼저 제안해 줘.
6. 테스트는 임시로 만든 git 레포에서만 해 줘. GitHub 레포 생성, 원격 푸시, 실제 PR 생성은 내가 허락하기 전에는 하지 마.

## 2. 배경과 목적

주변의 컴퓨터공학과 학생들이 바이브 코딩을 하면서 "왜 이렇게 했는지", "다른 방법은 없는지"를 고민하지 않고 AI가 알려준 대로 만들고 넘어가. whycommit은 커밋과 PR 시점에 에이전트가 사용자에게 면접 질문처럼 물어서, 자기 코드를 정확히 이해하고 넘어가게 하는 개인 학습 도구야.

- 형태: GitHub 공개 레포. Agent Skills 표준 형식의 스킬 3개 + Claude Code 플러그인 포장
- 대상: 처음부터 다른 사람도 쓰는 도구. 첫 버전은 Claude Code에서 검증
- 차별점: AI가 설명해 주는 도구가 아니라 AI가 사용자에게 묻는 도구. 커밋 제목 추천은 부가 기능이고 핵심은 퀴즈와 복습

## 3. 핵심 원칙 (반드시 지킬 것)

1. "이해한 내용"과 "이해하지 못한 내용"은 사용자의 답에서만 나온다. 에이전트가 대신 채우지 않고, 사용자가 직접 고쳐 쓸 수도 없다. 바꾸는 방법은 채점에 대한 이의 제기뿐이다.
2. "오늘 한 작업"과 "남은 작업"은 기록이라 자동으로 초안을 만들어도 된다. 단, 항상 사용자 확인을 거친다.
3. 커밋, 푸시, PR 생성·수정은 항상 미리보기를 보여주고 확인받은 뒤 실행한다.
4. 강제 푸시는 절대 하지 않는다. 이미 푸시된 커밋은 수정하지 않는다.
5. 학습 노트는 GitHub에 올라가지 않는다. 레포 밖(홈 폴더)에 저장한다.
6. "모르겠다"는 불이익이 아니다. 점수, 정답률, 등급 같은 평가 표현을 강조하지 않는다. 말투는 압박 면접이 아니라 모의 면접을 봐 주는 선배.
7. 채점은 엄격하게 한다. 핵심 이유를 말하지 못한 애매한 답을 맞다고 해 주지 않는다.
8. 스킬 지시문은 특정 에이전트에 묶이지 않게 쓴다. "에이전트가 질문한다"처럼 쓰고, 특정 에이전트 전용 도구 이름은 넣지 않는다. 선택지는 번호 목록을 보여주고 답을 기다리는 방식으로 쓴다.

## 4. 전체 구성

스킬 3개.

- commit: 커밋 제목 후보를 보여주고 고르게 한 뒤 커밋 (자주, 가볍게)
- quiz: 쌓인 변경으로 면접식 퀴즈를 보고 기록 (작업 단위가 끝날 때)
- review: 틀렸던 주제 복습 (원할 때)

Claude Code 플러그인으로 설치했을 때 `/whycommit:commit`, `/whycommit:quiz`, `/whycommit:review`로 부를 수 있어야 해. 플러그인 없이 표준 스킬로 설치했을 때 commit, quiz, review라는 이름이 다른 스킬과 충돌할 수 있는지 검토하고 이름 규칙을 제안해 줘.

세 스킬은 홈 폴더의 whycommit 폴더를 함께 쓴다. 그 안에 설정, 프로젝트별 학습 노트, 프로젝트별 상태가 들어간다.

## 5. commit 동작

1. git 레포인지, 스테이징된 변경이 있는지 확인한다. 없으면 변경된 파일 목록을 보여주고 전부 스테이징할지 묻는다.
2. 스테이징된 변경과 최근 커밋 기록을 읽는다. 기록에서 제목 형식과 언어를 파악한다. 기록이 없으면 `feat:`, `fix:` 형식에 사용자의 언어를 쓴다.
3. 제목 후보 3개를 만든다.
4. 번호 목록으로 보여준다: 후보 3개, 직접 입력, 다시 생성.
5. 고른 제목을 보여주고 확인받은 뒤 커밋한다. 본문은 비운다.
6. "퀴즈를 안 본 커밋이 N개 있어요" 한 줄을 보여준다.

이 스킬은 퀴즈를 내지 않고 푸시도 하지 않는다.

## 6. quiz 동작

### 6.1 준비

1. 현재 브랜치, 기본 브랜치, GitHub CLI(gh) 사용 가능 여부와 로그인 상태를 확인한다. 커밋하지 않은 변경이 있으면 퀴즈에 포함되지 않는다고 알린다.
2. 모드를 제안하고 확인받는다.
   - 작업 브랜치 → PR 모드
   - 기본 브랜치 → 마무리 모드
   - gh가 없거나 로그인이 안 돼 있으면: (1) 마무리 모드로 진행 (2) PR 본문만 만들어서 보여주기 중 선택
3. 범위를 정한다. "마지막으로 퀴즈를 본 커밋" 이후의 변경이 대상이다. 기록이 없으면 PR 모드는 기본 브랜치에서 갈라진 지점부터, 마무리 모드는 아직 푸시하지 않은 커밋부터. 새 변경이 없으면 알리고 끝낸다.
4. 변경과 주변 코드를 읽고 "설계 결정"을 뽑는다. 문서, 주석, 포맷팅, 설정값만 바뀐 변경이면 퀴즈 생략을 제안한다: (1) 건너뛰고 기록만 (2) 그래도 퀴즈 보기. 건너뛰면 6.3으로 간다.
5. 문제 수를 2~5개로 정한다. 기준은 줄 수가 아니라 설계 결정의 수. 학습 노트에서 이미 "이해함"인 주제는 뺀다. "3문제 낼게요"처럼 먼저 알린다.

### 6.2 퀴즈 (문제마다 반복)

1. 한 번에 하나씩 묻는다. 어느 파일의 어느 부분인지 짚는다.
2. 질문 유형은 세 가지다.
   - 왜 이렇게 했나 (이 선택의 이유)
   - 다른 방법은 없나 (대안과 장단점)
   - 이게 없으면 어떻게 되나 (동작 원리)
3. 금지: "무엇을 바꿨나"처럼 diff만 읽으면 답할 수 있는 질문, 변경과 무관한 CS 암기 질문.
4. 사용자는 답하거나 "모르겠다", "넘어가기", "그만"을 말할 수 있다. 코드를 보면서 답해도 된다.
5. 채점과 분기.
   - 맞고 답이 깊음 → 이해함, 다음 문제
   - 맞지만 얕음 → 꼬리 질문 1번. 꼬리 질문 결과는 본 질문과 따로 기록
   - 일부만 맞음 → 맞은 부분은 이해함, 빠진 부분은 이해 못 함으로 나눠 기록
   - 틀림 또는 "모르겠다" → 이해 못 함. 꼬리 질문 없음
   - "넘어가기" → 그 문제는 기록하지 않고 다음 문제
6. 꼬리 질문은 문제당 최대 1번(설정으로 변경 가능)이고 문제 수에 포함하지 않는다.
7. 이해 못 한 부분은 그 자리에서 바로 해설한다. 해설에는 정답, 이유, 대안과 장단점이 들어간다.
8. 채점에 동의하지 않으면 문제당 한 번 반론할 수 있다. 반론을 듣고 다시 판단한다.
9. "그만"이면 답한 문제까지만 학습 노트에 저장하고 끝낸다. PR과 커밋은 건드리지 않고 "마지막으로 퀴즈를 본 커밋"도 바꾸지 않는다.

### 6.3 기록 초안

1. 퀴즈 결과를 학습 노트에 먼저 저장한다. 뒤 단계가 실패해도 학습 기록은 남아야 한다.
2. "오늘 한 작업" 초안: 커밋과 변경 내용을 기준으로 쓰고, 현재 대화에서 작업 의도를 보탠다.
3. "남은 작업" 초안: 다음 순서로 모으고 항목마다 출처를 표시한다.
   - 기획 문서와 구현의 차이
   - 현재 대화에서 미루기로 한 것
   - 변경된 파일의 TODO 주석
   - gh가 있으면 열려 있는 관련 이슈
4. 기획 문서는 흔한 이름(README, docs 폴더, TODO 파일, 기획서 등)을 자동으로 찾는다. 못 찾으면 한 번 묻고 프로젝트별로 기억한다.
5. 초안을 번호를 붙여 보여주고 확인받는다. 사용자는 다음을 할 수 있고, "응"이라고 할 때까지 반복한다.
   - 말로 수정 ("2번 빼줘", "더 짧게")
   - "다시": 방향을 받아 새로 생성
   - "직접 쓸게": 어느 항목인지(오늘 한 작업, 남은 작업, 둘 다) 묻고 입력을 받는다. 줄바꿈이나 쉼표로 구분된 입력을 항목으로 나눈다. 문장은 고치지 않고 목록 형태로만 맞춘다. 사실 확인은 하지 않는다. 다시 미리보기를 보여준다. 이후 "다시"라고 하면 자동 초안으로 돌아갈 수 있다.
   - 비우기: 그 항목을 뺀다
6. 사용자가 "앞으로도 이렇게 써줘"라고 하면 그 작성 스타일을 설정에 저장한다. 직접 썼다는 이유만으로 자동 저장하지는 않는다.

### 6.4 본문 형식

네 개 항목이고 이름은 그대로 쓴다: 오늘 한 작업, 남은 작업, 이해한 내용, 이해하지 못한 내용.

- 기본: 오늘 한 작업과 남은 작업만 본문에 넣는다.
- "학습 내용 포함" 옵션을 켠 경우: 이해한 내용과 이해하지 못한 내용도 넣되 주제만 한 줄씩. 해설 전문은 학습 노트에만 둔다.

### 6.5 모드별 마무리

PR 모드
1. 브랜치를 푸시할지 확인한다.
2. PR 제목을 제안하고 본문 미리보기를 보여준 뒤 확인받고 PR을 만든다. 끝나면 링크를 보여준다.
3. 레포에 PR 템플릿이 있으면 지우지 않고 그 아래에 whycommit 부분을 추가한다.
4. 이미 PR이 있으면 본문 전체를 덮어쓰지 않고 whycommit 부분만 갱신한다. whycommit 부분을 식별할 수 있게 표시(예: HTML 주석 마커)를 두는 방법을 검토해 줘.
5. 사용자가 GitHub에서 whycommit 부분을 직접 고친 흔적이 있으면 말없이 덮어쓰지 않는다. 바뀌는 부분을 보여주고 확인받는다.

마무리 모드
1. 마지막 커밋을 아직 푸시하지 않았으면, 미리보기를 보여주고 확인받은 뒤 그 커밋의 메시지 본문에 기록한다.
2. 이미 푸시했으면 커밋을 건드리지 않고 학습 노트에만 저장했다고 알린다.
3. 푸시는 하지 않는다.

공통
1. "마지막으로 퀴즈를 본 커밋"을 현재 커밋으로 갱신한다.
2. 결과 요약과 "복습할 주제가 N개 쌓였어요" 한 줄을 보여준다.

## 7. review 동작

1. 범위: 레포 안에서 실행하면 그 프로젝트, 밖이면 전체. "전체"를 인자로 주면 모든 프로젝트.
2. 이해 못 한 주제 중에서 고른다. 한 번에 5개(설정으로 변경 가능), 여러 번 틀린 것과 오래된 것 먼저. 없으면 알리고 끝낸다.
3. 예전 질문을 그대로 반복하지 않고 같은 주제를 다른 각도로 묻는다. 원래 코드가 남아 있으면 그 코드를 짚어서 묻는다.
4. 채점 기준과 꼬리 질문 규칙은 quiz와 같다.
5. 맞히면 "이해한 내용"으로 옮기고 해결한 날짜를 적는다. 틀리면 그대로 두고 틀린 횟수를 올린 뒤, 이전과 다른 방식으로 다시 해설한다.
6. "3개 해결, 4개 남음"처럼 요약한다.

이 스킬은 git을 전혀 건드리지 않는다.

## 8. 데이터

홈 폴더의 whycommit 폴더 한 곳에 저장한다. macOS, Linux, Windows 모두에서 경로가 맞아야 한다.

- 설정 파일 하나. 첫 실행 때는 아무것도 묻지 않고 기본값으로 시작한다.
  - 문제 수 범위 (기본 2~5)
  - 문제당 꼬리 질문 수 (기본 1)
  - 본문에 학습 내용 포함 (기본 꺼짐)
  - 복습 문제 수 (기본 5)
  - 언어 (기본: 사용자가 쓰는 언어를 따라감)
  - 작성 스타일 (길이, 말투, 묶는 기준 등 자유 서술)
- 프로젝트별 폴더. 프로젝트는 원격 저장소 이름(owner/repo)으로 구분하고, 없으면 폴더 이름을 쓴다.
  - 학습 노트: 사람이 직접 열어 읽을 수 있는 마크다운이면서 스크립트가 안정적으로 읽고 고칠 수 있는 구조. 구체적인 파일 구성은 제안해 줘.
  - 항목 내용: 날짜, 주제, 질문, 내 답 요약, 해설, 상태(이해함 / 이해 못 함), 틀린 횟수, 해결한 날짜, 관련 파일과 커밋
  - 상태: 브랜치별 "마지막으로 퀴즈를 본 커밋", 기획 문서 위치, PR의 whycommit 부분을 마지막으로 쓴 내용(직접 수정 감지용)

학습 노트는 어떤 경우에도 레포 안에 만들지 않고 스테이징하지 않는다.

## 9. 스크립트로 보장할 것

스킬은 지시문이라 매번 똑같이 동작한다는 보장이 없어. 틀리면 안 되는 부분은 스크립트로 만들어 스킬에 넣어 줘.

- 학습 노트 항목 추가, 상태 변경, 틀린 횟수 증가
- "마지막으로 퀴즈를 본 커밋" 읽기와 쓰기
- 프로젝트 식별
- 마지막 커밋의 푸시 여부 확인 (커밋 수정 전 안전장치)
- 복습 대상 고르기

질문 생성, 채점, 해설처럼 판단이 필요한 부분은 지시문에 맡긴다.

### 9.1 실행 환경 조건 (필수)

스크립트는 아래 네 환경에서 같은 코드로, 같은 결과를 내야 해.

- Claude Code가 명령을 실행하는 셸 (운영체제와 관계없이)
- Windows PowerShell
- Windows Git Bash
- macOS 터미널 (zsh, bash)

이를 위해 지켜야 할 것.

1. 코드는 한 벌만 둔다. 셸 스크립트(.sh)와 PowerShell 스크립트(.ps1)를 따로 만들어 두 벌로 관리하지 않는다. 두 벌은 동작이 어긋나기 쉽고, .ps1은 Windows 기본 실행 정책에 막힐 수 있다.
2. 어느 셸에서나 같은 방식으로 실행되는 런타임을 쓴다. 외부 패키지 없는 Node.js를 우선 검토하고, 더 나은 방법이 있으면 장단점과 함께 제안해 줘. 그 런타임이 설치돼 있지 않을 때 어떻게 할지(안내 후 중단 등)도 같이 제안해 줘.
3. 실행 권한이나 셔뱅에 의존하지 않는다. 항상 런타임을 명시해서 실행한다.
4. 한글 등 비ASCII 텍스트(질문, 답, 해설)를 명령줄 인자나 파이프로 넘기지 않는다. Windows 콘솔의 코드 페이지 때문에 깨질 수 있다. 내용은 UTF-8 파일로 쓰고 스크립트에는 그 파일 경로만 넘긴다. 인자는 단순한 ASCII 옵션과 경로만 쓴다.
5. 파일은 항상 UTF-8(BOM 없음), 줄바꿈 LF로 읽고 쓴다. 레포에는 .gitattributes로 줄바꿈을 고정한다.
6. 경로는 직접 이어 붙이지 않고 런타임의 경로 기능을 쓴다. 홈 폴더 경로에 공백이나 한글이 들어 있어도 동작해야 한다 (예: C:\Users\홍길동).
7. 스크립트 안에서 git을 부를 때는 셸을 거치지 않고 인자 배열로 실행한다. 따옴표 규칙이 셸마다 달라서다.
8. 출력은 에이전트가 읽기 쉬운 형식(예: JSON)으로, 종료 코드는 성공 0, 실패 0 아님으로 통일한다.

### 9.2 자동 검증

네 환경을 사람이 일일이 확인하기 어려우니 GitHub Actions로 스크립트 테스트를 자동 실행하게 해 줘.

- macOS
- Windows + PowerShell
- Windows + Git Bash
- Linux

테스트에는 공백과 한글이 들어간 경로, 한글 내용의 저장과 읽기, 줄바꿈 유지가 포함돼야 해. 워크플로 파일은 만들어 두되, 푸시는 내 허락 후에 해.

## 10. 레포 구성과 README

- 기본은 표준 스킬 폴더 구조. 그 위에 Claude Code 플러그인 매니페스트를 얹는다.
- 다른 사람이 명령 한 줄로 설치할 수 있게 한다.
- 라이선스는 MIT.
- README는 한국어로 쓴다. 들어갈 내용:
  - 문제의식 (2장의 내용)
  - 무엇을 하는 도구인지와 사용 예시 화면
  - 설치 방법, 필요한 것 (git, Claude Code, 스크립트 런타임, PR 모드는 GitHub CLI)
  - 동작을 확인한 환경 (macOS, Windows PowerShell, Windows Git Bash)
  - 학습 노트가 어디에 저장되는지, GitHub에 올라가지 않는다는 점
  - 한계: 퀴즈 답을 AI에게 물어보는 건 막을 수 없다. 강제하는 도구가 아니라 멈춰서 생각하게 만드는 도구다. 노트는 로컬에만 있어서 컴퓨터를 바꾸면 사라질 수 있다.
  - 지원 에이전트: Claude Code에서 검증함. Codex 등 다른 에이전트는 표준 형식이라 동작할 가능성이 높지만 아직 확인하지 못함. 테스트 결과 제보 환영.

## 11. 검증할 시나리오

임시 git 레포에서 아래를 모두 확인해 줘.

1. 평소 커밋: 제목 후보 선택 후 커밋, 안 본 커밋 수 안내
2. 작업 브랜치에서 퀴즈 → PR 본문 작성 (실제 PR 생성은 내 허락 후)
3. 기본 브랜치에서 마무리 모드: 푸시 전에는 커밋 본문에 기록
4. 마무리 모드: 푸시 후에는 커밋을 건드리지 않고 노트에만 저장
5. 문서만 바뀐 변경: 건너뛰기 제안
6. PR에 커밋 추가 후 재실행: 새 변경만 퀴즈, whycommit 부분만 갱신
7. PR 본문을 직접 고친 뒤 재실행: 덮어쓰기 전에 확인
8. 채점 이의 제기
9. 중간에 "그만"
10. "직접 쓸게"로 남은 작업 작성, 쉼표 구분 입력
11. "앞으로도 이렇게"로 스타일 저장 후 다음 실행에 반영
12. review: 프로젝트 범위, "전체" 범위, 맞히면 이동, 틀리면 횟수 증가
13. gh가 없을 때의 선택지
14. 학습 노트가 레포 안에 생기지 않고 스테이징되지 않는지
15. 스크립트 테스트가 9.1의 네 환경에서 모두 통과하는지 (9.2의 자동 검증)
16. 공백과 한글이 들어간 홈 폴더 경로, 한글 질문·답·해설의 저장과 복습에서 글자가 깨지지 않는지
